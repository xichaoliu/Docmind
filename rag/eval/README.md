# 查询改写评测集

对比 **查询改写（`condense_question`）** 与 **直接检索** 的命中率。

## 为什么测试集全是多轮

`condense_question` 第一行就是：

```python
if not history:
    return question
```

**单轮对话根本不改写。** 所以测试集里每条都必须带历史轮次，否则两组结果必然完全一样，测不出任何东西。

## 语料

`/Users/xichaoliu/Desktop/测试文档/apple软件许可协议 .md`（26,119 字符，切分后 73 个 chunk）

选它的原因：条款密集、事实具体（金额、期限、法规编号），而且**各章节共享词汇**（"非商业""公开共享""限制"在多个条款里都出现）——这正是让"它/这个"这类指代产生真实歧义的条件。

> **不需要**把它传到线上索引里。跑分脚本会在内存里单独建索引，不碰 `rag/faiss_index/`。

## 测试集构成（42 条）

| 类型 | 条数 | 最后一轮长什么样 | 测什么 |
| --- | --- | --- | --- |
| `pronoun` 指代型 | 14 | "那**它**包不包括？"、"需要满足什么条件？" | 指代只能在历史里找到先行词 |
| `ellipsis` 省略型 | 14 | "最短期限**呢**？"、"H.264 呢？" | 主题被省略，只剩名词短语 |
| `continuation` 话题延续 | 8 | "还有别的吗？"、"那我要怎么关掉？" | 完全靠上文才能确定在问什么 |
| `control` 对照组 | 6 | "责任上限是多少钱？"（自包含） | **验证改写不会有害** |

对照组很关键：改写不是只会带来好处——它可能给已经完整的问题**加上多余的限定**，反而把正确结果挤掉。所以必须有对照组来量化这个风险。

## 命中判定

```
命中 = top-k 里存在一个 chunk 同时包含该条 gold 里的全部关键词
```

**当前 42 条的 gold 关键词都验证过**：真实切分后落在同一个 chunk 内，所以判定是可靠的。

关键词都选了文档里唯一的字符串（比如 `"5、6、7、8、9、11、12 和 13"`、`"故意不当行为或重大疏忽"`），避免误命中。

## 怎么跑

```bash
cd rag
python -m eval.run_rewrite_eval                          # 默认语料
python -m eval.run_rewrite_eval --doc /path/to/doc.md    # 换语料
python -m eval.run_rewrite_eval --k 4 --fetch-k 1000     # 调参
```

**前提**：Ollama 在跑（改写要调模型）。如果连不上，`condense_question` 的兜底会返回原问题，脚本仍能跑完，但会显示"改写实际改变了查询的 0 条"——这时候的结果没有意义。

## 实测结果

用当前代码（`k=4`、`fetch_k=1000`、qwen2.5 改写）在 2026-10-06 跑出的真实数据：

```
类型              条数      直接检索      查询改写      变化
------------------------------------------------------------------
指代型             14          14%          64%       +50%
省略型             14          14%          71%       +57%
话题延续            8           0%          75%       +75%
对照组              6          50%          50%        +0%
------------------------------------------------------------------
合计               42          17%          67%       +50%
```

- 改写实际改变了查询：**36/42 条**（其余 6 条是没带历史的对照组）
- **改写赢 21 条，改写输 0 条**
- 改写质量抽样：

| 原问题 | 改写后 |
| --- | --- |
| 那有什么限制？ | 嵌入字体到文档有哪些限制？ |
| 那如果只是看，不操作呢？ | 最多几台设备可以仅观看而不需要操作？ |
| 具体在哪儿设置？ | 内容缓存功能的具体关闭步骤在哪里？ |

## 两个比"提升 50 个点"更重要的发现

### 发现 1：对照组的 50% 暴露了检索本身的短板

对照组是**自包含、无需改写**的问题，本该接近 100%，实测只有 50%。逐条诊断失败的 3 条：

| id | 问题 | 正确答案位置 | top-4 检索到了什么 |
| --- | --- | --- | --- |
| 37 | 责任上限是多少**钱**？ | 第 44 chunk（含 `250`） | 全部协议、虚拟化、MPEG-4… |
| 38 | 受哪个**州**的法律管辖？ | 第 47 chunk（含 `加利福尼亚`） | MPEG-4、全部协议、EA2005… |
| 41 | 包不包括 **Boot ROM**？ | 第 2 chunk | 非商业用途、迁移软件、内容缓存… |

**三条全栽在同一类词上：数字、专有名词、英文缩写。**

这是纯向量检索的固有短板——语义相近不等于字面匹配。而修法就是路线图 **2.2 混合检索**（BM25 补关键词一路）。**这个评测顺带给混合检索提供了实测论据。**

> 反过来想：如果当初没设计对照组，结论就会是"改写把命中率从 17% 提到 67%，效果很好"，而**检索本身 50% 的短板完全不会被发现**。对照组是这份测试集里性价比最高的 6 条。

### 发现 2：改写会丢意图

`id=6`（"备份副本可以复制几份？" → "那它包不包括？"）被改写成：

```
那它包不包括？  →  备份副本可以复制几份？
```

**模型把问题改回了上一轮，把"包不包括"这个当前意图整个丢了。** 所以这条两组都没命中。

这类失败在汇总数字里看不出来（它既不算"改写赢"也不算"改写输"），但值得单独盯——改写模型的输出需要校验，不能无条件信任。

## 脚本还会输出什么

除上面的表格外：

- **改写实际改变了查询的条数** —— 如果远小于总条数，说明改写没在工作
- **改写赢 / 改写输 的具体条目** —— "改写输"的案例最有分析价值
- **改写效果抽样** —— 直观看到模型把"那它包不包括？"改成了什么

对照这轮实测，正确的读法是：**看分类不看总和**。总和 17%→67% 很漂亮，但拆开看，对照组的 50% 才是真正该先动手的地方。

## 几个必须注意的点

**① history 是近似的**

真实对话里，每轮用户提问后面还有助手回答。测试集只提供用户轮次（因为我没有真实回答），condense 模型看到的上下文比线上少一半。

这**不影响两组对比的有效性**（两组用的是同一个 history），但**绝对命中率会低于线上**。看相对差异，不要看绝对值。

**② 只有 73 个 chunk，区分度有限**

语料小、章节密集时，随机命中的概率也不低。所以**别只看总和**，要看分类：

- 对照组应该接近 100%（如果很低，说明检索本身有问题）
- 指代/省略型的差距才是改写的真实收益

**③ 换语料要重新验证 gold**

改 `--doc` 后，原来的 gold 关键词可能在新文档里不存在。建议加一道校验：

```python
for it in items:
    for g in it["gold"]:
        assert g in doc_text, f"id={it['id']} 的关键词 {g!r} 不在语料里"
```

**④ 这个评测只用一份文档**

所以它测的是**chunk 级**的检索区分度，不是**文档级**。如果要测多文档场景（比如"它的参数呢"在两个不同产品文档间产生歧义），需要准备多份文档再扩充测试集。

| 文件 | 说明 |

## 字段说明

```json
{
  "id": 1,                                    // 1-42 连续
  "type": "pronoun",                          // pronoun / ellipsis / continuation / control
  "turns": ["软件里的字体可以嵌入到我的文档里吗？"],   // 历史轮次（对照组为空数组）
  "test_question": "那有什么限制？",              // 被测的最后一轮
  "gold": ["字体册", "嵌入限制"],                // 命中判定关键词
  "note": "第 2E 条"                           // 正确来源（人工核对用，评测不使用）
}
```
