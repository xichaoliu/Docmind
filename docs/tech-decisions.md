# 技术选型记录

记录项目关键技术决策及理由，方便复习和面试时快速回顾。

## 后端语言分工：Java + Python 双服务

**决策**：Java（Spring Boot）负责业务层，Python（FastAPI）负责 AI/RAG 层，两者通过内部 HTTP/SSE 通信，不合并成一个服务。

**理由**：
- 已有 Python RAG demo，重写成本高，且 Python 生态（LangChain、FAISS）在 RAG 场景更成熟
- Java 是目标岗位之一的技能要求，需要在作品集中体现
- 职责边界清晰：凡是"和用户、数据、业务流程有关"的放 Java（会话管理、鉴权、文档元数据持久化）；凡是"和模型、向量有关"的留在 Python（检索、生成、切块）
- 现实中也是常见架构模式（Java 主站 + Python AI 服务），面试可直接对应实际工作场景

---

## 数据库：PostgreSQL（而非 MySQL）

**决策**：业务数据（document / conversation / message）存储于 PostgreSQL。

**理由**：
1. **JSONB 支持**：`message.citations` 字段是半结构化数据（引用来源数组），JSONB 类型可直接存储并支持对内部字段查询、索引，比额外建关联表更省事，也比 MySQL 的 JSON 类型成熟。
2. **与向量库的潜在整合**：若后续将向量库从 FAISS 换成 pgvector（PostgreSQL 的扩展），可以让业务数据和向量数据共用一个数据库实例，减少一个独立容器。MySQL 没有对应方案。
3. **两者在 Spring Boot 接入方式几乎一致**，不影响 Java 后端技术栈学习本身，选型不存在"哪个更好上手"的顾虑。
4. 近年新项目中 PostgreSQL 使用率上升，写在简历上不吃亏。

**权衡**：MySQL 生态资料更多、更主流，如果目标公司明确要求 MySQL 经验，是同样合理的选择，本项目场景下差异不大。

## ORM 框架：MyBatis-Plus（而非 Spring Data JPA）

**决策**：用 MyBatis-Plus 替代最初计划的 JPA。

**理由**：
1. **SQL 更透明可控**：出问题时能直接在日志里看到实际执行的 SQL 语句，比 JPA 的方法名推导查询更易调试。
2. **JSONB 映射更省心**：用内置 `JacksonTypeHandler` 即可处理 JSONB 字段，不需要像 JPA 那样引入第三方依赖（`hibernate-types`）。
3. **符合团队/个人技术背景**：贴近纯 SQL 思维，比 JPA"配置优于编码"的风格更快上手。
4. 建表脚本手动维护（`schema.sql`），表结构变化有据可查，比 JPA 自动建表（`ddl-auto`）更接近生产环境实践。

**权衡**：JPA 在 Java 岗位招聘要求里出现频率也很高，如果目标公司明确要求 JPA/Hibernate 经验，可以作为后续补充学习的方向；两者思路相通，迁移成本不高。

## Spring Boot 版本：3.5.6（而非默认的 4.x）

**决策**：项目使用 Spring Boot 3.5.6，Java 21，未使用 2026 年新发布的 4.x 系列。

**理由**：
1. **4.0 是"世代重置"版本**：底层升级到 Jakarta EE 11、Jackson 3，依赖坐标发生重命名（如 `spring-boot-starter-web` → `spring-boot-starter-webmvc`），是破坏性变更，不是小版本升级。
2. **第三方生态适配可能滞后**：截至选型时，未能确认 MyBatis-Plus 等常用库是否已完整适配 Spring Boot 4 的 Jakarta EE 11 基线。历史上（Spring Boot 2→3 迁移时）MyBatis 生态的适配就曾滞后于 Spring Boot 本身的发布。
3. **3.x 生态资料更成熟**：文档、Stack Overflow、AI 辅助编码工具的训练数据都以 3.x 为主，排查问题效率更高。
4. **面试场景更贴近实际**：目前企业存量项目仍以 3.x 为主，3.x 经验更符合当前招聘市场的实际需求。
5. **3.5 虽然已停止官方安全补丁（EOL），但不影响功能使用**，本项目是学习/展示用途，不是生产部署，这一点可接受。

**权衡**：4.x 是未来趋势，长期看早晚要迁移；但当前阶段优先级是"稳妥推进项目进度"，不是"追新"，选择更保守的版本线是合理的工程判断。

## Java 版本：21（LTS）

**决策**：使用 OpenJDK 21，而非 17。

**理由**：本地环境已安装 21，是长期支持版本（LTS），与 Spring Boot 3.x 完全兼容，比 17 能用上更多新特性（如虚拟线程），面向未来更合理，不存在兼容性问题。

---

## 前端框架：React（而非继续使用 Vue 3）

**决策**：新项目使用 React + TypeScript，尽管过往经验以 Vue 3 为主。

**理由**：目标岗位中 React 需求更高；Vue 3 的组件化、响应式思维、工程化经验可以平滑迁移，属于同一技术圈层内的横向扩展，学习成本可控。

---

## 状态管理：TanStack Query（服务端数据）+ Zustand（客户端状态）

**决策**：不用单一状态管理方案覆盖所有场景，按数据来源拆分。

**理由**：
- 服务端数据（会话列表、文档列表、历史消息）有其特有的问题（缓存、加载态、失败重试、多组件间共享同一份数据），TanStack Query 专门解决这类问题，比在 Zustand 里手写 loading/error 逻辑更省心。
- 客户端本地状态（当前选中会话、侧边栏展开状态、登录态）用 Zustand，API 简洁，不需要 Provider 包裹，选择性订阅性能更好。
- 两者职责不重叠，混用不冲突。

---

## SSE 而非 WebSocket

**决策**：流式问答接口使用 SSE（Server-Sent Events），而非 WebSocket。

**理由**：
- 通信方向是单向的（服务端流式推送给客户端），不需要 WebSocket 的双向通信能力
- SSE 基于标准 HTTP，浏览器原生支持断线重连、实现和调试成本更低（可以直接用 curl 验证）
- 和现有的 HTTP 请求/响应模型更契合，Java 网关层做透传时改造成本更小
